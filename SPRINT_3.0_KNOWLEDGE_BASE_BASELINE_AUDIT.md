# SPRINT 3.0 KNOWLEDGE BASE / RAG BASELINE AUDIT

## A. Executive Summary
This audit establishes the baseline status of the Knowledge Base / RAG system before Sprint 3 implementation. While the database schema contains foundational models (`KnowledgeDocument`, `KnowledgeChunk`) and the pgvector extension is enabled, the actual RAG processing engine (`KnowledgeBase`) is a stub. There are no production document extractors, ingestion routes, upload handlers, or orchestrator RAG pipelines currently configured.

---

## B. Existing Memory Architecture
Memory is retrieved contextually using 1536-dimensional embeddings generated by `OpenAIEmbeddingProvider`. Retrieval queries use exact similarity checks in the `Memory` table, bounded by `relevanceThreshold` (0.3) and `maxMemories` (5). Context is injected into the user message via `<user_memories>` XML blocks.

---

## L. Memory vs Knowledge Boundary
- **Memory (User-specific):** Facts, preferences, and goals related to individual users. Saved in the `Memory` table and queried using user-scoped locks.
- **Knowledge (System/SOPs):** Reference documents, playbooks, guidelines, and SOPs. Saved in `KnowledgeDocument` and `KnowledgeChunk` tables.

---

## M. Security
Current gaps:
- Path traversal: Checked inside `DocumentAnalyzerTool` but missing production gateway middleware.
- Input safety: Sanitization of document injections is needed.
- Malware scanning: None exists.

---

## N. User / Tenant Isolation
**Critical Gap:** The `KnowledgeDocument` schema lacks a `userId` field or relation. Without this, documents uploaded by User A are visible to User B, violating isolation boundaries. We must introduce a `userId` column in `schema.prisma`.

---

## O. Chunking
No chunking utilities currently exist in the codebase. We must implement a text-slicing tool (e.g., recursive character chunking with custom token size and overlap defaults).

---

## P. Vector Retrieval
The pgvector similarity retrieval queries are stubbed. We will need to write raw SQL similarity checks (cosine distance `<=>`) inside the repository layer to query chunks.

## AB. Known Risks
- **Double Embed Overhead:** Performing a memory search AND a knowledge search requires generating two sets of embeddings for each query, increasing latency and API costs.
- **Prisma vector fallback:** Prisma does not natively support pgvector queries without raw SQL bindings.
