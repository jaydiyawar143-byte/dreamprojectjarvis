# JARVIS Task Engine V2 Implementation Plan

> **PLAN ONLY — NOTHING HERE IS IMPLEMENTED.**
> **CURRENT** = verified in code today. **PROPOSED V2** = this plan.
> **FUTURE** = deliberately deferred beyond V2.
> No application code, schema, migration or task record was changed to produce
> this document.
>
> Source of truth: [`JARVIS_TASK_LIFECYCLE_V2.md`](./JARVIS_TASK_LIFECYCLE_V2.md).
> Written 2026-09-23 against Scheduler V1 as shipped.

---

## 1. Executive Summary

**What Scheduler V1 already solves (CURRENT).** A spoken request becomes a
durable task, is planned into exactly one authorised tool call, is scheduled to
an unambiguous instant, and runs **exactly once** even across replicas. Two
independent compare-and-sets — `claimSchedule` on `scheduledAt` and `startTask`
on `status` — make duplicate execution unreachable, and the two-replica tests
(`scheduler-v1.test.ts` K, K2) hold that line.

**What V2 solves.** V1 protects against running work twice. It does not protect
against **losing** work. Three gaps, all verified:

| Gap | Effect |
|---|---|
| Claim consumes `scheduledAt`, then the process dies before `startTask` | task sits `PENDING` with no schedule, **silently never runs** |
| A crash while `RUNNING` | nothing can move it; stuck forever |
| Tool succeeded but the completion write failed | the execution evidence says it ran, the task says `RUNNING` — they disagree |

Plus one modelling gap: `PENDING` means four different things, so "recorded and
abandoned" is indistinguishable from "recorded and deliberately not scheduled".

**The central finding that shapes this plan.** The repository **already has**
a durable execution-recovery layer, and it is wired at boot:

```
ToolExecution   executionId, idempotencyKey, ownerId, leaseUntil,
                heartbeatAt, reconciliationAttempts
                @@unique([userId, toolId, idempotencyKey])
ToolExecutionStatus  PENDING APPROVED EXECUTING SUCCEEDED FAILED
                     UNKNOWN RECONCILING SAFE_TO_RETRY CANCELLED
StartupRecovery      stale EXECUTING  -> UNKNOWN
                     stale RECONCILING -> UNKNOWN     (index.ts:104)
```

> ### CORRECTION (2026-09-23, after V2.1 implementation)
>
> **An earlier revision of this plan said `Task.executionId` points at a
> `ToolExecution` row. That is NOT universally true, and the plan below has
> been corrected throughout.** Repository inspection during V2.1 established
> the actual shape:
>
> | Layer | What is true |
> |---|---|
> | **Task lifecycle** | `PENDING RUNNING COMPLETED FAILED`, owned by `TaskService`, unchanged |
> | **`Task.executionId`** | generated by `TaskExecutionService`, persisted on `Task`, and passed **into** `ToolExecutor`. It is a **correlation id**, not a foreign key |
> | **`AuditLog`** | the executor writes `action: "tool.execute"` with `metadata.executionId` for **every** execution. This is the durable execution evidence on the **general** task path |
> | **`ToolExecution`** | a real journal with leases, heartbeats and idempotency — but written only by **execution-journal-aware tools** that receive the journal as a dependency (the Meta write tools). `ToolExecutor` itself takes **no journal**; its constructor is `(registry, permissionChecker, approvalManager, auditLogger)`. **No `ToolExecution` row exists for an ordinary task execution such as `system.status`.** |
>
> So `ToolExecution` **cannot be assumed to be the universal task execution
> journal**, and `StartupRecovery` — which operates on that journal — does not
> see ordinary task executions at all.
>
> **This does not change the V2 direction, and it does not create a need for a
> new journal.** Do not invent one. It changes what recovery may *rely on*:
> see the note at the end of §7.

So **V2 must not build a second lease system on `Task`, and must not invent a
second execution journal either.** Where a `ToolExecution` row exists, it
already answers "did it actually run?" with a lease, a heartbeat and an explicit
`UNKNOWN` for ambiguous writes. What is missing is a **link** from a task to its
execution evidence. That link is one nullable column — but it is a correlation
id, and on its own it is **not** a recovery mechanism (§5.2, §7).

**FUTURE beyond V2:** automatic retry, recurring schedules, multi-step durable
workflows, `RUNNING` cancellation, agent-to-agent orchestration.

## 2. Scheduler V1 Baseline — must remain unchanged

**CURRENT.** V2 changes none of these except where §8 states explicitly and
argues for it.

| Component | Behaviour that must survive |
|---|---|
| **Scheduler loop** | 60 s interval, one sweep at a time, immediate first sweep on boot, ≤20 due per sweep, `ShutdownLifecycle`-tracked as `EXTERNAL_SIDE_EFFECT` |
| **Atomic schedule claim** | ONE conditional `updateMany`, `count === 1` decides the winner. Safe across replicas with no lock service |
| **Task start** | `startTask` → `transitionOwned`, `WHERE status = expectedFrom`. The second, independent gate |
| **Planner at execution time** | re-plans from the task **as it reads at run time**; no plan is persisted |
| **ToolExecutor** | the sole path to a side effect: registry, params, permission against the caller's role, approval gate, shutdown gate, deadline, **audit**. It writes the AUDIT row, not a `ToolExecution` row — the journal is a dependency of individual journal-aware tools |
| **Status model** | `PENDING RUNNING COMPLETED FAILED`; `canTransitionTask` the only rule table |
| **API contracts** | `POST/GET/PATCH /api/v1/tasks*`, `POST/DELETE /:id/schedule`, `GET/POST/PATCH/DELETE /command-center/tasks*` |
| **Tests** | `scheduler-v1` (50), `task-execution-v1`, `task-planner-v1`, `task-conversation-v11`, `core-v1*`, `command-center-task-visibility`, `work-request-goal`, `schedule-phrase-timezone` — all must stay green unchanged |
| **`SCHEDULED_RUN_ROLE = "member"`** | a schedule never runs with more authority than it was created with |
| **Todo/work boundary** | `excludeCreatedBy` on the command-center `PATCH`/`DELETE`; null-safe `createdByIsNot` |

## 3. V2 Goals

**PROPOSED.** In priority order, each tied to a verified gap.

| # | Goal | Why | Gap closed |
|---|---|---|---|
| G1 | **Prevent lost scheduled execution** | the claim/start window silently drops work | L4 |
| G2 | **Recover orphaned RUNNING work** | a crash strands a task permanently | L3 |
| G3 | **Reconcile task state with the available execution evidence** | tool succeeded, DB write failed → the two disagree. "Evidence" is the audit row on the general path, and a `ToolExecution` row only where a journal-aware tool wrote one | new |
| G4 | **Distinguish scheduled from intentionally unscheduled** | `PENDING` is four states | L5 |
| G5 | **Make intent explicit for NEW records only** | historical intent is unrecoverable | L5 |
| G6 | **Preserve backward compatibility** | old rows must keep working, unmodified | — |
| G7 | **Preserve duplicate-execution protection** | non-negotiable; every change is measured against it | — |
| G8 | **Single state ownership** | `updateOwned` bypasses the transition table | L7 |
| G9 | **Establish cancellation semantics** | a `PENDING` task cannot be stopped | L2 |
| G10 | **Prepare for explicit retry — design only** | `FAILED` is final and must stay so until designed | L1 |
| G11 | **Preserve normal todo behaviour exactly** | two lifecycles, one table | — |

## 4. Non-Goals

**V2 will NOT implement any of these.**

| Excluded | Why |
|---|---|
| **Automatic retry** | re-running a side-effecting tool without an idempotency contract is how a campaign gets created twice. `SAFE_TO_RETRY` exists in the journal as a *distinct* state precisely because "failed" and "safe to redo" are different facts |
| **`RUNNING` cancellation** | `ToolExecutor` offers no cooperative cancellation; "cancelled" would claim something JARVIS cannot deliver |
| **Recurring schedules / cron** | V1 is one-time by design; recurrence multiplies every recovery question |
| **Multi-step durable workflows** | the planner produces ONE action on purpose |
| **Agent-to-agent orchestration, self-repair, MCP, learning** | none is blocked by task state; all are separate programmes |
| **New task statuses beyond `CANCELLED`** | the fix for overloaded `PENDING` is metadata, not more enum values |
| **Changing `ToolExecutor`** | it is the execution authority. V2 reads the evidence it emits, and does not change how it executes |

## 5. Proposed Data Model

**PROPOSED.** Minimum viable: **two** new nullable columns. Everything else is
rejected below with reasons.

### 5.1 `claimedAt` — REQUIRED for V2.1

```prisma
claimedAt DateTime? @map("claimed_at")
```

| | |
|---|---|
| **Why** | The claim currently destroys `scheduledAt`, which is both the claim marker *and* the only record of when the task was meant to run. A crash after the claim leaves no evidence a claim ever happened. `claimedAt` separates "when it should run" from "someone took it" |
| **Written by** | `claimSchedule` (set), the recovery sweep (cleared to re-arm), `startTask` — see §8 |
| **Read by** | `findDueScheduled` (must be null), the orphan sweep, the frontend |
| **Migration** | additive nullable column + index; existing rows get `NULL` = "unclaimed", which is correct for every one of them |
| **Required for** | **V2.1** — this is the lost-execution fix |

### 5.2 `executionId` — REQUIRED for V2.3

```prisma
executionId String? @map("execution_id")
```

| | |
|---|---|
| **Why** | `ToolExecutionResult.executionId` already exists and is returned by `executeTask` — **and is then discarded**. Persisting it gives every task run a **correlation id** that also appears in `AuditLog.metadata.executionId`, so "which run did this task perform?" stops being an inference. **It is a correlation id, NOT a recovery mechanism on its own**: knowing the id does not tell you the outcome unless something durable recorded one — see §7 |
| **Written by** | `TaskExecutionService`, immediately before `executor.execute` |
| **Read by** | the `RUNNING` recovery sweep; future retry; future analytics |
| **Migration** | additive nullable; `NULL` on old rows means "we don't know", which is honest |
| **Not a foreign key** | **and it could not be one.** No `ToolExecution` row exists for an ordinary task execution; the universal durable record is the `AuditLog` row the executor writes under the same id. A soft correlation reference, explicitly documented |
| **Required for** | **V2.3** |

### 5.3 `executionMode` — PROPOSED for V2.4, and **not** the recovery mechanism

```prisma
executionMode String? @map("execution_mode")   // IMMEDIATE | SCHEDULED | UNSCHEDULED
```

**Evaluated honestly, as asked.** The brief suggested this field might carry the
design. It should not.

- **It does not solve lost execution.** `claimedAt` does, more directly and with
  one less inference step. If `executionMode` were the orphan signal, recovery
  would read "SCHEDULED but no schedule" — which is *also* what a cancelled
  schedule looks like.
- **It does solve intent (G4/G5).** `UNSCHEDULED` records "recorded, no time
  given, nothing will run it" at creation time — the plan-only and
  not-executable paths — which is genuinely underivable later.

**Recommendation: keep it, demote it.** Metadata for intent and for the UI, not
a recovery primitive. Deliver it in V2.4 after the two recovery fixes land.

| Decision | Recommendation |
|---|---|
| **Enum or string?** | **String column with a Zod union in `packages/core`**, matching how `status` is already modelled (`Task.status` is `String`, validated by `TaskStatusSchema`). A native Postgres enum makes rollback harder for no gain here |
| **Nullable?** | **Nullable**, no default backfill. `NULL` = "created before V2, intent unknown" — a real and distinct fact |
| **Default for new rows?** | Set explicitly at every creation site; never defaulted in the database, so a missing value is always a code bug rather than a silent guess |

**Allowed combinations (PROPOSED):**

| `executionMode` | `status` | `scheduledAt` | `claimedAt` | Meaning |
|---|---|---|---|---|
| `IMMEDIATE` | `PENDING` | `null` | `null` | within a request; transient |
| `SCHEDULED` | `PENDING` | set | `null` | armed, waiting — **the only scheduler-eligible shape** |
| `SCHEDULED` | `PENDING` | set | set | claimed, not started (transient, or orphaned) |
| `UNSCHEDULED` | `PENDING` | `null` | `null` | deliberately not scheduled; **never runs** |
| any | `RUNNING`/`COMPLETED`/`FAILED` | `null` | — | past the scheduler |
| `NULL` | any | any | `null` | historical row; §13 |

**Forbidden:** `UNSCHEDULED` with `scheduledAt != null`; any `scheduledAt != null`
with a terminal status (already invariant 12 in the audit).

### 5.4 Fields evaluated and REJECTED for V2

| Field | Verdict | Why |
|---|---|---|
| `leaseUntil` | **reject for V2** | `ToolExecution.leaseUntil` exists with `StartupRecovery` acting on it, so where a journal row exists a second lease on `Task` would be a second source of truth. Where one does NOT exist — the ordinary task path — a lease would be new machinery, and V2.3 must decide deliberately rather than inherit it by assumption |
| `heartbeatAt` | **reject for V2** | same reasoning. Tasks do not run; executions do |
| `claimToken` | **reject** | the existing CAS already yields exactly one winner via `count === 1`. A token adds a column to re-prove something already proven |
| `attempt` | **defer to FUTURE** | meaningless without a retry contract (§12). Adding it early invites someone to increment it |
| `recoveryCount` | **reject** | diagnosis belongs in logs and the journal's `reconciliationAttempts`, not in a column on user-owned work |
| `ownerId` / replica id | **reject** | the claim is safe without knowing who won. Recording it tempts "recover only my own rows", which is wrong with N replicas |

> **Principle applied:** `Task` models *user-owned intent*. Execution is
> recorded elsewhere — universally in the `AuditLog` row the executor writes,
> and additionally in a `ToolExecution` row **when a journal-aware tool wrote
> one**. Lease, heartbeat and idempotency are execution concerns and belong to
> that layer, not to `Task`.

## 6. State Transition Matrix

### 6.1 IMPLEMENTED TODAY

| CURRENT | NEXT | OWNER | TRIGGER | GUARDS | SIDE EFFECTS |
|---|---|---|---|---|---|
| — | `PENDING` | `TaskService.createTask` | creation | userId | row written |
| `PENDING` | `RUNNING` | `TaskExecutionService` | `executeTask` step 4 | ownership, PENDING-only, allowlist, CAS on status | `startedAt` set |
| `PENDING` | `RUNNING` | `TaskSchedulerService` | `runOne` when re-planning failed | same CAS | `startedAt` set |
| `PENDING` | `RUNNING` | `PATCH /tasks/:id/status`, `task.updateStatus` | explicit | `canTransitionTask` | `startedAt` set |
| `RUNNING` | `COMPLETED` | `TaskExecutionService` | `status==="completed" && result.success` | CAS | `completedAt` set, `error` cleared |
| `RUNNING` | `FAILED` | `TaskExecutionService` / `TaskSchedulerService` | any other outcome | CAS | `error` set, **no `completedAt`** |
| `COMPLETED`/`FAILED` | — | — | — | — | terminal (`TRANSITIONS = []`) |
| *(todo only)* `*` → `COMPLETED`, `COMPLETED` → `PENDING` | | `updateOwned` | checkbox | `NOT status=RUNNING`, `excludeCreatedBy` | **bypasses `canTransitionTask`** |

### 6.2 PROPOSED V2 — additions only

| CURRENT | NEXT | OWNER | TRIGGER | GUARDS | SIDE EFFECTS |
|---|---|---|---|---|---|
| `PENDING` *(claimed, stale)* | `PENDING` *(re-armed)* | **`ScheduleRecoverySweep`** (new) | `claimedAt` older than threshold, still `PENDING` | CAS on `claimedAt`, `status=PENDING` | `claimedAt` → `null`; task becomes due again |
| `RUNNING` | `FAILED` | **`RunningRecoverySweep`** (new) | `startedAt` older than threshold **and** the execution evidence does not show it still running | CAS on status, evidence consulted via `executionId` | `error` = "interrupted by a restart" |
| `RUNNING` | `COMPLETED` | **`RunningRecoverySweep`** (new) | evidence shows the run succeeded — **available only where a journal row exists**; see §7 | CAS on status | `completedAt` set — repairs crash window D |
| `RUNNING` | `FAILED` | **`RunningRecoverySweep`** (new) | evidence shows the outcome is ambiguous | CAS | `error` states the run is ambiguous; **never auto-retried** |
| `PENDING` | `CANCELLED` | `TaskService.cancelTask` (new) | user or JARVIS | ownership, PENDING-only, CAS | `scheduledAt` **and** `claimedAt` cleared in the same statement |
| `CANCELLED` | — | — | — | — | terminal |
| `FAILED` | `PENDING` | — | — | — | **FUTURE only** (§12). Not in V2 |

No other state is introduced. `RUNNING → recovery state` is deliberately
**not** a new status: recovery resolves into the existing terminal states,
because "we recovered it" is not a thing the user needs a status for.

## 7. Scheduler Crash Recovery

**The highest-priority V2 problem.** No database transaction can include an
external tool call; every design below assumes the tool call is outside the
transaction boundary and that something OTHER than the task — the execution
evidence — is the record of what actually happened.

**What that evidence actually is (CURRENT, corrected).** Two different things,
and the difference decides what each window below can recover:

| Path | Durable record | Carries an outcome? |
|---|---|---|
| **Every** task execution | `AuditLog` row, `action: "tool.execute"`, `metadata.executionId` | a coarse `result` — `success` / `failure` / `rejected` / `pending` — **written after the call returns** |
| **Journal-aware tools only** (the Meta write tools) | `ToolExecution` row, with lease, heartbeat and idempotency key | yes, including `UNKNOWN` for an ambiguous write, and `StartupRecovery` already sweeps it |

A crash mid-call means the executor never reached its own audit write, so on
the general path **there is no durable outcome for that attempt at all**. That
is a fact about the current architecture, not a gap to paper over.

### Window A — claim, then crash before `startTask`

| | |
|---|---|
| **CURRENT** | `scheduledAt` cleared; task `PENDING`; **never runs again**, silently. Indistinguishable from a stale row |
| **DESIRED V2** | detected and re-armed automatically |
| **Data needed** | `claimedAt` |
| **Mechanism** | claim sets `claimedAt` and **keeps** `scheduledAt` (§8). A sweep re-arms rows with `status=PENDING AND claimedAt < now - threshold` by clearing `claimedAt` |
| **Duplicate risk** | **none.** No tool ran — `executeTask` was never reached. Re-arming returns the task to the state it was in before the claim |
| **Idempotency risk** | none, same reason |

### Window B — `startTask` succeeds, then crash before `executeTask`

| | |
|---|---|
| **CURRENT** | task `RUNNING` forever; nothing can move it |
| **DESIRED V2** | resolved to `FAILED` with a truthful reason |
| **Data needed** | `executionId` |
| **Mechanism** | `RunningRecoverySweep`: `RUNNING`, `startedAt` beyond threshold, **no audit row for this `executionId`** → the executor was never reached → `FAILED` |
| **Duplicate risk** | none — nothing ran |
| **Idempotency risk** | none |

> **Corrected.** As implemented in V2.1, `executionId` is written WITH the
> `PENDING -> RUNNING` claim, so it is populated before the executor is called
> and a null value no longer distinguishes window B. The signal that does is
> the **absence of an audit row for that `executionId`**: the executor audits
> every terminal outcome, so no audit row means the call never returned. This
> is still the case V2 can resolve with the most confidence — but it is a
> lookup against `AuditLog`, not an inference from a null column.

### Window C — crash while the tool call is in flight

| | |
|---|---|
| **CURRENT** | task `RUNNING` forever. **Where a journal-aware tool ran**, its row is left `EXECUTING` and moved to `UNKNOWN` by the existing `StartupRecovery`. **On the general path there is no journal row and no audit row** — the crash beat the audit write — so nothing durable records the attempt |
| **DESIRED V2** | the task stops claiming to be running. Where a journal row exists, follow it: `UNKNOWN` → `FAILED`. Where none exists, `FAILED` with a message that says the outcome **could not be confirmed** |
| **Data needed** | `executionId`, plus whatever evidence that id can be looked up in |
| **Mechanism** | reconcile the task against the available evidence — journal row if there is one, audit row otherwise, and **neither** is also an answer |
| **Duplicate risk** | **only if V2 retried, which it must not.** The provider may or may not have applied the side effect; that is precisely what `UNKNOWN` means |
| **Idempotency risk** | **high if mishandled.** The rule: an ambiguous execution is reported, never redone. `SAFE_TO_RETRY` is the journal's separate, deliberate state and only it may ever be re-run — a FUTURE decision (§12) |

### Window D — tool completed, the completion write failed

| | |
|---|---|
| **CURRENT** | the work **happened**. `executeTask` returns `ok: true` with the execution (honest), but the task stays `RUNNING`. The audit row for that `executionId` records `result: "success"`; the task disagrees |
| **DESIRED V2** | reconciliation repairs the task to `COMPLETED` |
| **Data needed** | `executionId` |
| **Mechanism** | audit row `success` (or journal `SUCCEEDED`, where one exists) + task `RUNNING` → `COMPLETED` |
| **Duplicate risk** | none — this only writes DB state; the tool is not called |
| **Idempotency risk** | none |

**Summary:** A and B are fully recoverable with no side-effect risk. D is
repairable. **C is not "recoverable" — it is reportable**, and V2's job there is
to stop pretending the task is still running.

> ### BINDING NOTE FOR V2.2 AND V2.3 (added 2026-09-23)
>
> **V2.2 and V2.3 must design recovery against the execution evidence that
> actually exists, and must NOT assume a `ToolExecution` row exists for every
> task.** Concretely:
>
> 1. **Do not query `ToolExecution` by `Task.executionId` as the primary
>    lookup.** For an ordinary task execution there is no such row, and the
>    query will correctly return nothing — which must not be read as "the run
>    did not happen".
> 2. **`AuditLog` (`action: "tool.execute"`, `metadata.executionId`) is the
>    universal evidence** and is the lookup V2.3 should be built on. Confirm
>    before implementing that it can be queried efficiently by that id; it is
>    inside a JSON column and is **not indexed today**, which is a real
>    implementation cost to size rather than assume away.
> 3. **A `ToolExecution` row, where one exists, is strictly better evidence**
>    — it carries `UNKNOWN`, leases and idempotency. Use it when present;
>    never require it.
> 4. **"No evidence" is a legitimate third answer**, distinct from "succeeded"
>    and "failed". A crash mid-call leaves it, and the honest resolution is
>    `FAILED` with a message saying the outcome could not be confirmed — never
>    a retry.
> 5. **Do not invent a new execution journal**, and do not widen
>    `ToolExecution` to cover every tool, as a side effect of building
>    recovery. If universal journalling is wanted, that is its own decision
>    with its own plan.
>
> `Task.executionId` alone provides **correlation, not recovery**. It tells you
> which run to ask about; it does not tell you what happened.

## 8. Claim / Lease Design

**Evaluated, as asked.**

| Option | Verdict |
|---|---|
| **A. `claimedAt`** | **CHOSEN** — one column, directly encodes the failure window, preserves scheduling history |
| **B. `leaseUntil` on Task** | rejected for V2 — where a journal row exists it duplicates `ToolExecution.leaseUntil`, and where none exists it is new machinery V2.3 should adopt deliberately, not by default |
| **C. Heartbeat on Task** | rejected — a task does not run; its execution does, and that already heartbeats |
| **D. `executionId`** | **CHOSEN, for a different job** — correlation for reconciliation (§7 C/D), not claiming. It identifies the run; the evidence that says what happened lives in `AuditLog`, and in `ToolExecution` only where a journal-aware tool wrote one |
| **E. Claim token** | rejected — `count === 1` already elects one winner atomically |
| **F. Combination** | **A + D**, and nothing else |

### The proposed claim

**CURRENT**
```sql
UPDATE "Task" SET scheduled_at = NULL
WHERE id = ? AND created_by = 'jarvis'
  AND status = 'PENDING' AND scheduled_at IS NOT NULL;
-- count === 1 wins.  scheduledAt destroyed; claim leaves no trace.
```

**PROPOSED V2**
```sql
UPDATE "Task" SET claimed_at = now()
WHERE id = ? AND created_by = 'jarvis'
  AND status = 'PENDING'
  AND scheduled_at IS NOT NULL
  AND claimed_at IS NULL;          -- <- the new compare
-- count === 1 wins.  scheduledAt PRESERVED.
```
with `findDueScheduled` gaining `AND claimed_at IS NULL`.

**Why this is still exactly-once.** It remains a **single conditional
`updateMany`** whose `WHERE` contains the compare and whose `SET` performs the
set. `claimed_at IS NULL` is the same shape of guard `scheduled_at IS NOT NULL`
was. Two replicas still produce one `count === 1`. **The concurrency argument is
unchanged; only the column carrying it moves.**

**What it buys:** `scheduledAt` survives as history (better UI, better
analytics), and an orphaned claim is visible instead of erased.

> **This modifies a mechanism §"MUST NOT change" flags as load-bearing.** That
> is deliberate and is why it is stated here in full rather than done quietly.
> It requires: the migration in §13, the K/K2 two-replica tests re-run
> unchanged, and a new test proving the claim is still exactly-once with the
> new predicate. If that evidence does not come back clean, the change does not
> ship.

**Multi-replica safety is preserved end to end:** no leader election, no lock
service, no queue — one atomic statement, as today.

## 9. RUNNING Crash Recovery

**PROPOSED.** Detecting "`RUNNING` but abandoned" needs two signals, not one.

```
candidate  = status = RUNNING AND started_at < now() - threshold
verdict    = consult the execution evidence for execution_id
```

| Evidence for `execution_id` | Verdict | Task becomes |
|---|---|---|
| no audit row and no journal row | the call never returned | `FAILED` — "outcome could not be confirmed" |
| audit `result: "success"` | it worked (window D) | `COMPLETED` |
| audit `result: "failure"` / `"rejected"` | it failed | `FAILED` with the recorded reason |
| journal `UNKNOWN` *(journal-aware tools only)* | ambiguous write | `FAILED` — "outcome could not be confirmed", **never retried** |
| journal `EXECUTING` with a live lease *(journal-aware tools only)* | **still running** | leave alone |

The last row is what would make a threshold safe — **a long legitimate run
protected by its own live lease** rather than by a generous number. **That
protection exists only for journal-aware tools.** On the general path there is
no lease, so a long-running ordinary tool is protected only by the threshold
itself, which makes choosing it a real decision rather than a formality (§21-1).

**Threshold.**
- Must be **configurable** (`JARVIS_TASK_RECOVERY_AFTER_MS`), matching the
  existing `JARVIS_*_INTERVAL_MS` convention.
- `ToolExecutor`'s 30 s default deadline is a **floor**, not the answer: a
  task's total wall time also spans the planner (20 s abort) and approval waits.
- False positives are reduced by the evidence check, not by the number — but
  only a journal-aware tool has a live lease proving it is still running, so on
  the general path the number carries more weight than an earlier draft of this
  plan implied.

> **This is an explicit design decision (§21-1).** A number must be chosen by a
> human before implementation. This plan deliberately does not pick one.

## 10. Lost Execution Recovery

**PROPOSED.** With `claimedAt` in place (§8), the three `PENDING` shapes become
distinguishable **without reinterpreting anything**:

| Shape | Meaning | Scheduler action |
|---|---|---|
| `PENDING`, `scheduledAt` set, `claimedAt` null | armed | **pick it up when due** |
| `PENDING`, `scheduledAt` set, `claimedAt` old | **orphaned claim** | **re-arm** — clear `claimedAt` |
| `PENDING`, `executionMode = UNSCHEDULED` | deliberately not scheduled | **never touch** |
| `PENDING`, `executionMode = IMMEDIATE` | in-request transient | **never touch** |
| `PENDING`, `executionMode = NULL` (historical) | intent unknown | **never touch** — §13 |

The scheduler's eligibility predicate stays positive: it selects on
`scheduledAt IS NOT NULL AND claimed_at IS NULL AND status = 'PENDING' AND
created_by = 'jarvis'`. Work is picked up because it is **armed**, never because
it merely failed to be excluded. A historical row with no `scheduledAt` cannot
become eligible by accident under any value of `executionMode`.

## 11. Cancellation Contract

**PROPOSED — V2.5, and only if §21-2 is answered yes.**

| Question | Answer |
|---|---|
| **Which states** | `PENDING` only. **`RUNNING` is NOT cancellable** — no cooperative cancellation exists in `ToolExecutor` |
| **Who requests** | **Both** the user (REST) and JARVIS (a tool) |
| **Who performs** | One method, `TaskService.cancelTask` — the integration rule: one implementation, two callers |
| **`scheduledAt`** | cleared **in the same statement** that sets `CANCELLED`, together with `claimedAt`. Sequencing them separately leaves a window where the sweep could claim a cancelling task |
| **Visible?** | **Yes.** Cancellation is a recorded decision, not a delete. `deleteOwned` already exists and is a separate act |
| **Idempotent?** | **Yes** — cancelling an already-`CANCELLED` task returns success without a second write. The CAS makes the repeat match zero rows; the service reports success |
| **Terminal?** | Yes. `TRANSITIONS.CANCELLED = []` |

Cancelling an `UNSCHEDULED` or historical `PENDING` task is technically
identical; whether "cancel" is the right word for work never scheduled is
**§21-4**.

## 12. Retry Contract — FUTURE ONLY

**NOT IN V2.** Documented so that no one implements it by accident.

`TRANSITIONS.FAILED = []` is a deliberate refusal to guess a retry semantics.
Before `FAILED → PENDING` can exist, all of the following must be decided:

| Requirement | Why |
|---|---|
| **A new `executionId` per attempt** | for a journal-aware tool, `@@unique([userId, toolId, idempotencyKey])` means a reused key is the *same* execution, not a new one. For every other tool there is no such constraint, so nothing at the storage layer would stop a duplicate side effect — which makes the idempotency policy below more important, not less |
| **An idempotency key policy** | reusing the key de-duplicates (safe, possibly a no-op); a new key genuinely re-runs (possibly a duplicate side effect). This choice *is* the retry semantics |
| **`attempt` counter** | bound retries; currently absent on purpose |
| **Which failures are retryable** | only `SAFE_TO_RETRY`. **`UNKNOWN` must never be retried automatically** — the provider may already have applied the write |
| **User-visible or automatic** | a user-pressed "Retry" is a fresh decision with a fresh consent. Automatic retry of side-effecting work is what this plan refuses |

**Recommendation:** when it comes, the first increment is **user-initiated retry
of `SAFE_TO_RETRY` executions only**. Automatic retry stays out of scope
indefinitely.

## 13. Existing Data Migration

**PROPOSED.** Three additive nullable columns, **no backfill, no `UPDATE` of any
existing row.**

```sql
ALTER TABLE "Task" ADD COLUMN "claimed_at"     TIMESTAMP(3);
ALTER TABLE "Task" ADD COLUMN "execution_id"   TEXT;
ALTER TABLE "Task" ADD COLUMN "execution_mode" TEXT;
CREATE INDEX "Task_claimed_at_idx" ON "Task"("claimed_at");
-- the sweep's query; mirrors Task_scheduled_at_status_idx
```

| Existing row | `claimedAt` | `executionMode` | Reads as | Behaviour |
|---|---|---|---|---|
| `COMPLETED` | `NULL` | `NULL` | done | unchanged |
| `FAILED` | `NULL` | `NULL` | failed | unchanged |
| `PENDING` + `scheduledAt` set | `NULL` | `NULL` | **armed and unclaimed — correct** | still runs when due |
| `PENDING` + `scheduledAt` null (**stale**) | `NULL` | `NULL` | intent unknown | **never picked up** — it has no `scheduledAt`, so it fails the positive predicate |
| Normal todos (`createdBy = null`) | `NULL` | `NULL` | untouched | the scheduler's `createdBy = 'jarvis'` filter excludes them, as today |

**Why no backfill.** Setting historical `PENDING + scheduledAt=null` rows to
`UNSCHEDULED` would *assert* an intent the data cannot support: those rows are a
mix of genuinely-unscheduled and abandoned work, and the audit established that
they are not separable. `NULL` says "we do not know", which is true. The
frontend already renders them as **"Unscheduled"** — a label, not a claim about
intent.

**The only behavioural change for an existing row** is that an orphaned-claim
row could be re-armed — but no historical row can be, because none has
`claimedAt` set. **Every existing row behaves exactly as it does today.**

## 15. JARVIS Work Query

**CURRENT:** the `tasks.list` tool passes `excludeCreatedBy: JARVIS_TASK_CREATOR`
(`ambient-adapter.ts:189`), so **JARVIS cannot see its own work when asked in
chat.** Core V1 already ships a separate `task.list` tool that selects
`createdBy = "jarvis"`.

| Option | Assessment |
|---|---|
| **A. Modify `tasks.list`** | **Reject.** It is the *todo* tool; folding work in merges two lifecycles at the one surface most likely to be read aloud, and a user asking "what's on my list?" would hear machine work |
| **B. Add `work.list`** | **Reject as new work** — it already exists as `task.list`. Adding a third name for the same query is the duplication AGENTS.md forbids |
| **C. Extend `tasks.list` with a mode filter** | **Reject.** Pushes the todo/work boundary into a *parameter*, where a model chooses it. A security-relevant boundary decided by an argument the model fills in is strictly weaker than two tools with two allowlists |
| **D. Grant the existing `task.list` to the conversational agent, unchanged** | **RECOMMENDED** |

**Recommendation (PROPOSED, not implemented): option D.** Change one agent
policy allowlist so `task.list` is reachable in conversation. No new tool, no
new endpoint, no new query, no parameter carrying a boundary.

Assessed against the criteria asked for: **security** — the boundary stays
compile-time, in the allowlist; **ownership** — `task.list` is already
userId-scoped; **UI separation** — untouched, the dashboard already separates
them; **agent self-awareness** — this is the entire point, JARVIS gains the
ability to answer "what have you got scheduled?"; **analytics** — one canonical
work query rather than two; **todo semantics** — `tasks.list` keeps meaning
exactly what it means today.

## 16. Observability

**PROPOSED.** Reuse the existing convention exactly — one line of
`console.log(JSON.stringify({ level, event, ...meta }))`, the shape
`task_scheduler_*` already uses. **No payloads, no titles, no secrets.**

| Event | When | Fields |
|---|---|---|
| `task_schedule_claimed` | claim wins | `taskId`, `scheduledAt`, `latenessMs` |
| `task_execution_started` | `startTask` succeeds | `taskId`, `executionId`, `toolId` |
| `task_execution_settled` | terminal | `taskId`, `executionId`, `status`, `durationMs` |
| `task_claim_recovered` | orphaned claim re-armed | `taskId`, `claimedAgeMs` |
| `task_running_recovered` | `RUNNING` resolved | `taskId`, `executionId`, `evidence` (`audit` \| `journal` \| `none`), `resolvedTo` |
| `task_cancelled` | cancellation | `taskId`, `requestedBy` |
| `task_recovery_sweep_completed` | **every** sweep | `candidates`, `reArmed`, `resolved`, `durationMs` |

The last one follows the lesson already learned in Scheduler V1: a sweep that
logs only when it finds something is indistinguishable from a dead one. **Every
sweep logs, including an empty one.**

## 19. Rollback Strategy

| Change | Rollback | Risk |
|---|---|---|
| `claimed_at` column | leave in place; revert code | **low.** Old code ignores it. One caveat below |
| `execution_id` column | leave; revert code | **none** — write-only until V2.3 |
| `execution_mode` column | leave; revert code | **none** — `NULL` already means "unknown" |
| **`CANCELLED` status value** | **cannot be cleanly reverted** | **high** — see below |
| Recovery sweeps | stop them | **low** — the pre-V2 stuck-task behaviour returns |
| Claim predicate change | revert repository | **medium** — see below |

**Dropping a column is never the rollback.** Every column here is additive and
nullable; leaving it costs nothing and dropping it loses evidence.

**Claim predicate, mid-rollback (multi-replica).** During a rolling deploy, old
and new code run together. Old `claimSchedule` clears `scheduledAt`; new keeps
it and sets `claimedAt`. Both are single conditional updates on the same row, so
**exactly-once still holds** — a task claimed by old code has no `scheduledAt`
and is invisible to new code; one claimed by new code has `claimedAt` set and
old code, which does not read that column, could claim it again. **Therefore:
during V2.1 rollout and rollback, the recovery sweep must be disabled** (its
interval set to 0) so a re-armed row cannot meet old code. Stated as a deploy
precondition, not left to chance.

**`CANCELLED` is the one-way door.** Once written, reverted code cannot parse
it. Mitigations, in order: (1) ship V2.5 last and separately; (2) keep the value
in the Zod union for at least one release *before* anything writes it, so a
revert target already understands it; (3) if a revert is needed after rows
exist, roll **forward** with a fix rather than back.

## 20. Invariants

**Must hold before and after V2:**

1. Two scheduler replicas must never execute the same claimed task.
2. Every status change is a compare-and-set pinning the expected current value.
3. Every task query is filtered by `userId`, unconditionally.
4. Only `createdBy = "jarvis"` rows are scheduler-eligible.
5. Normal todos remain independent of JARVIS work; the `excludeCreatedBy`
   guards on `PATCH`/`DELETE` stay.
6. `ToolExecutor` is the sole execution authority; no agent, sweep or route
   bypasses it.
7. **No external side effect is ever assumed atomic with DB state.**
8. A scheduled run carries no more authority than an immediate one.
9. `FAILED` never sets `completedAt`.

**New in V2:**

10. **Intentionally unscheduled work is never picked up by the scheduler** —
    eligibility is a positive predicate on `scheduledAt`, never an exclusion.
11. `RUNNING` is not cancellable.
12. **Historical records are never silently reinterpreted**; no migration
    backfills intent.
13. **An ambiguous execution (`UNKNOWN`) is reported, never redone.**
14. Recovery is idempotent: running any sweep twice changes nothing.
15. A recovery sweep never calls a tool. It only reconciles database state
    against the execution evidence that exists.
17. **No component may assume a `ToolExecution` row exists for a given task.**
    Its absence means "this tool does not journal", never "the run did not
    happen".
16. `scheduledAt != null` implies `status = PENDING`.

## 21. Open Design Decisions

Genuinely requiring a human choice. No assumption is hidden elsewhere in this
plan.

**21-1. RUNNING recovery threshold.** How long may a task be `RUNNING` before it
is a *candidate*? **An earlier draft said the journal check makes false
positives nearly impossible — that is true only for journal-aware tools.** On
the general path there is no lease, so the threshold is the only protection for
a long legitimate run and must be chosen with that in mind. `ToolExecutor`'s
30 s deadline is a floor; planner (20 s) and approval waits extend real wall
time. **Blocks V2.3.**

**21-1b. Should ordinary tool executions be journalled at all?** Making
`ToolExecution` universal would give every task a lease and an `UNKNOWN` state,
and would make recovery uniform. It would also change the executor's
dependencies and write a row per execution. **Out of scope for V2 and
deliberately not assumed anywhere in this plan** — but it is the decision that
would most simplify V2.3, and it should be taken explicitly rather than drifted
into.

**21-2. Is cancellation in V2 or V2.x?** It is the only change with an awkward
rollback (§19) and the only one users will ask for by name. Shipping it last and
separately is the safe reading, but that is a product call. **Blocks V2.5.**

**21-3. Retry scope and timing.** Recommended default: user-initiated only, on
`SAFE_TO_RETRY` only, never automatic. Needs explicit approval before any work.

**21-4. Final `executionMode` semantics.** Specifically: (a) is `IMMEDIATE`
worth persisting at all, given it is transient within one request? (b) may an
`UNSCHEDULED` task later be scheduled, moving to `SCHEDULED` — and if so, who
may do that? (c) is "cancel" the right verb for work that was never scheduled?

**21-5. `task.list` in conversation (§15-D).** Granting it lets JARVIS answer
"what have you got scheduled?". It also means work tasks appear in a spoken
answer, which is a product judgement about what JARVIS should volunteer.

**21-6. Does V2.1's claim change ship with the sweep disabled first?** §19 makes
this a deploy-safety requirement; confirming it is an operational decision.

---

## 22. Final Recommendation

Implement in this order:

1. **V2.1 — claim durability.** The only change that stops work being lost
   today. Self-contained, reversible, needs no new intent model.
2. **V2.2 — `executionId` link.** One column, write-only, zero risk. It is the
   prerequisite for everything in V2.3.
3. **V2.3 — RUNNING recovery.** Unblocks once 21-1 is answered. Closes the
   remaining two crash windows and repairs the evidence/task disagreement.
   Must be built on the evidence that actually exists — see the binding note
   at the end of §7.
4. **V2.7 — grant `task.list`.** Independent of all the above, one line, ships
   whenever; gives JARVIS sight of its own work.
5. **V2.4 — `executionMode`.** Modelling clarity and honest UI labels. Valuable,
   but it fixes no failure mode, so it follows the fixes.
6. **V2.6 — observability.** Fold each event in with its phase; formalise here.
7. **V2.5 — cancellation.** Last and separate, because of the rollback shape.

**Steps 1–3 are the plan.** They are where work is being lost and stranded
today, they need no new concepts, and every one of them is additive and
reversible. Everything after is improvement rather than repair.

**Do not start V2.1 before 21-6 is confirmed**, and do not start V2.3 before
21-1 is chosen.
